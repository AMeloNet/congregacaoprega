# PBL-002 — Publicação funcional controlada

Status: **proposta documentada em 23/09/2026; primeiro incremento especificado
em [PBL-002A](PBL-002A.md), sem infraestrutura funcional criada**. Relacionada a
[IDN-001C](IDN-001C.md), [PBL-001](PBL-001.md),
[ADR-0001](../decisoes/0001-arquitetura-inicial.md),
[ADR-0002](../decisoes/0002-identidade-gerenciada.md) e à
[proposta de hospedagem](../operacao/hospedagem-proposta.md).

## Objetivo e limites

Publicar a aplicação integrada em um ambiente técnico controlado para validar o
frontend, a API NestJS, o PostgreSQL gerenciado e o login Auth0 sob HTTPS. A
etapa usa apenas contas e dados fictícios e mantém o transporte de e-mail em
captura, sem entrega externa.

PBL-002 não publica reservas, equipamentos ou programação funcionais, não
autoriza pessoas reais, não configura produção e não substitui a prévia UI-001.
A contratação de plano pago, domínio, remetente externo, múltiplas réplicas e
liberação do piloto operacional exigem decisão própria.

## Atores e permissões

| Ator | Permissão nesta etapa |
| --- | --- |
| Mantenedor/operador | Configurar o ambiente, aplicar migrations pelo job exclusivo, validar o deploy e executar recuperação |
| Conta técnica de migration | Aplicar somente o histórico versionado no banco alvo; não executar a aplicação |
| Conta da aplicação | Consultar e alterar os dados exigidos pela API com privilégio mínimo; não alterar schema |
| Pessoa de teste | Autenticar-se pelo tenant Auth0 da etapa e usar somente dados fictícios aos quais foi associada |
| Público não autenticado | Abrir a interface e iniciar login; não consultar dados protegidos nem a captura de e-mail |

## Pré-condições

- O commit a publicar está incorporado à `main` e os checks obrigatórios estão
  aprovados.
- O ambiente usa um Web Service que executa o `Dockerfile`; um Static Site não
  atende ao contrato porque `AccessApp` consulta `/api/session`.
- Há um PostgreSQL 18 gerenciado, vazio ou na versão anterior suportada, sem
  dados reais, com credenciais separadas para migration e aplicação.
- Há um tenant/aplicação Auth0 de teste do tipo **Regular Web Application**, com
  conexão de banco, verificação e recuperação de e-mail configuradas.
- A URL HTTPS final do Web Service é conhecida antes de cadastrar callback,
  logout, origem e links de convite.
- Existe um mecanismo operacional restrito e testado para observar a captura de
  e-mails. A [PBL-002A](PBL-002A.md) mantém a captura apenas na memória e
  permite observação por uma rota operacional assinada, com expiração e consumo
  único. Bootstrap e convites no ambiente remoto permanecem bloqueados até que
  segredo, cliente e controles dessa rota sejam validados sem gravar tokens em
  logs.

## Topologia e origem

O Web Service executa a API NestJS e serve `apps/web/dist` pelo mesmo host. O
frontend usa caminhos relativos `/api/...`; `APP_BASE_URL`,
`AUTH0_CALLBACK_URL` e `AUTH0_LOGOUT_URL` devem derivar da URL HTTPS canônica:

```text
APP_BASE_URL=https://<servico-funcional>.onrender.com
AUTH0_CALLBACK_URL=https://<servico-funcional>.onrender.com/api/auth/callback
AUTH0_LOGOUT_URL=https://<servico-funcional>.onrender.com/
```

Essa topologia não precisa habilitar CORS. A API não deve responder com origem
curinga nem aceitar credenciais entre origens. Se frontend e API forem separados
no futuro, outra mudança deve definir `FRONTEND_ORIGIN`, permitir somente a
origem HTTPS exata, habilitar credenciais de modo explícito e testar preflight,
origens rejeitadas e cookies. Não inferir origem a partir de cabeçalho enviado
pelo cliente.

## Serviços e responsabilidade

| Componente | Proposta da etapa | Responsabilidade |
| --- | --- | --- |
| Aplicação | Render Web Service, uma réplica | Executar NestJS, servir o frontend compilado e expor saúde |
| Banco | PostgreSQL 18 gerenciado, inicialmente Neon Free | Persistir identidade, vínculos, convites e auditoria |
| Identidade | Auth0 Free, tenant de teste | E-mail/senha, verificação, recuperação e Authorization Code |
| E-mail da aplicação | Captura controlada | Impedir entrega externa e permitir inspeção somente ao operador autorizado |
| Migrations | Job exclusivo e serializado | Aplicar exatamente o histórico Prisma antes da nova aplicação |

Uma única réplica é obrigatória nesta etapa porque sessões e captura estão em
memória. Reiniciar ou suspender o serviço encerra sessões e perde mensagens
capturadas. Não apresentar esse ambiente como altamente disponível.

## Variáveis e segredos

| Nome | Classe | Regra |
| --- | --- | --- |
| `NODE_ENV` | configuração | `production` no Web Service |
| `PORT` | configuração gerenciada | fornecida pelo Render; a API escuta em `0.0.0.0` |
| `DATABASE_URL` | segredo | credencial de privilégio mínimo usada pela aplicação |
| `AUTH0_ISSUER` | configuração | emissor HTTPS exato do tenant, com barra final |
| `AUTH0_CLIENT_ID` | configuração | cliente da Regular Web Application da etapa |
| `AUTH0_CLIENT_SECRET` | segredo | armazenado somente no cofre do ambiente |
| `AUTH0_AUDIENCE` | configuração | audiência exata validada pela API |
| `AUTH0_CALLBACK_URL` | configuração | URL HTTPS canônica terminada em `/api/auth/callback` |
| `AUTH0_LOGOUT_URL` | configuração | URL HTTPS permitida de retorno após logout |
| `APP_BASE_URL` | configuração | origem HTTPS canônica usada pela interface e convites |
| `SESSION_SECRET` | segredo | aleatório, exclusivo do ambiente e com pelo menos 32 caracteres |
| `BOOTSTRAP_SECRET` | segredo | aleatório e distinto do segredo de sessão |
| `CAPTURE_OPERATOR_SECRET` | segredo | exclusivo da rota operacional PBL-002A, distinto dos demais e com pelo menos 32 caracteres |
| `EMAIL_TRANSPORT` | configuração | obrigatoriamente `capture` nesta etapa |
| credencial de migration | segredo operacional | separada de `DATABASE_URL`, injetada somente no job de migration |

Valores reais não entram em Git, Issues, PRs, comandos registrados, capturas ou
logs. Cada ambiente usa chaves e clientes próprios. A ausência, formato inválido
ou transporte diferente de `capture` deve impedir a inicialização.

## Publicação e migrations

1. Selecionar o commit aprovado e registrar seu SHA imutável.
2. Construir o mesmo `Dockerfile` revisado pela CI; não publicar somente
   `apps/web/dist`.
3. Validar a URL do banco e o ambiente alvo sem imprimir a credencial.
4. Executar, em job exclusivo e serializado, `pnpm --filter
   @congregacaoprega/database db:migrate:deploy` com a credencial de migration.
5. Verificar status e schema drift conforme
   [migrations](../banco/migrations.md). Falha interrompe a publicação; não
   marcar migration manualmente como aplicada.
6. Iniciar uma única réplica com a conta de aplicação, aguardar
   `/api/health/live` e `/api/health/ready`, e só então executar os testes de
   fumaça.
7. Validar interface, `/api/session`, login, callback, logout, cookies, origem e
   captura com contas fictícias. Só executar bootstrap/convites depois de
   aprovar a observação restrita da PBL-002A.
8. Registrar commit, horário, comandos sem segredos, resultados, consumo e
   limitações. A publicação continua técnica e não libera pessoas reais.

## Falhas e recuperação

- Falha de migration impede iniciar a nova versão. Diagnosticar e corrigir por
  nova migration; nunca usar `db push`, reset ou edição do histórico aplicado.
- Falha de prontidão mantém o deploy fora de uso. A saúde viva, sozinha, não
  comprova acesso ao banco.
- Falha de Auth0 exige restaurar a configuração anterior ou corrigir URLs/chaves
  antes de liberar o teste; não desabilitar validação de emissor, audiência,
  nonce, state ou PKCE.
- Reverter a aplicação não reverte o banco. As migrations atuais são aditivas;
  futuras mudanças devem declarar compatibilidade e recuperação antes do deploy.
- Antes de dados relevantes, executar backup lógico e restauração em banco
  descartável. A existência do backup não comprova recuperação.
- Em reinício, considerar sessões encerradas e captura perdida. Convites
  persistidos continuam no banco e devem ser revogados ou reemitidos conforme o
  procedimento, sem recuperar tokens em texto aberto.

## Critérios de aceitação

| ID | Resultado verificável |
| --- | --- |
| PBL2-01 | O ambiente funcional publica um SHA aprovado por Web Service e o mesmo processo serve interface e API sob HTTPS |
| PBL2-02 | A aplicação inicia somente com todas as variáveis válidas; segredos não aparecem no repositório, build, respostas ou logs |
| PBL2-03 | PostgreSQL 18 gerenciado usa credenciais distintas de migration e aplicação, e a conta da aplicação não altera schema |
| PBL2-04 | O job exclusivo aplica todo o histórico em banco vazio e na versão anterior, não reaplica migrations e detecta drift |
| PBL2-05 | `/api/health/live` comprova processo vivo e `/api/health/ready` só aprova com banco acessível |
| PBL2-06 | A raiz carrega `AccessApp`, `/api/session` responde pela mesma origem e falha de API é apresentada sem exibir a demonstração como dado funcional |
| PBL2-07 | Auth0 aceita somente callback/logout/origem cadastrados; login, callback, sessão e logout funcionam com conta fictícia e cookies seguros |
| PBL2-08 | CORS permanece desabilitado na topologia de mesma origem; não há origem curinga nem requisição credenciada para origem não autorizada |
| PBL2-09 | `EMAIL_TRANSPORT=capture` não envia rede; captura e tokens são acessíveis somente pelo canal operacional restrito da PBL-002A e nunca por resposta não autorizada ou log |
| PBL2-10 | Uma falha de migration, configuração, banco ou Auth0 interrompe a promoção e deixa evidência sem segredo |
| PBL2-11 | Rollback da aplicação e restauração do banco são ensaiados separadamente; nenhuma etapa usa reset em banco persistente |
| PBL2-12 | A prévia PBL-001 continua isolada no commit estático validado até decisão explícita de substituição |
| PBL2-13 | O ambiente permanece com uma réplica e documenta encerramento de sessões/perda da captura após reinício ou suspensão |
| PBL2-14 | Nenhuma conta, e-mail ou dado pessoal real é usado; a publicação não é apresentada como produção ou piloto operacional |

Os [cenários PBL-002](../testes/cenarios-pbl-002.md) devem ser implementados e
executados antes de qualquer configuração persistente ser declarada validada.
